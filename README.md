# TrustVault — secure document sharing

Confidential documents (salary letters, contracts, drawings, audits) shared only with **named users**, with
per-document read/edit grants, **immediate revocation**, and a **tamper-evident audit trail**.
Stack: React + Vite + TypeScript + Tailwind · Supabase Auth / Postgres (RLS) / private Storage / Edge Functions (Deno).

## Run locally
Prereqs: Node ≥ 20.11, Docker, [Supabase CLI](https://supabase.com/docs/guides/cli).

The frontend requires a reachable Supabase project for real sign-in and account creation. Starting only Vite
does not create accounts. On Windows, run these commands in PowerShell:
```powershell
npm install
npx supabase start
npx supabase db reset
npx supabase status
Copy-Item .env.example .env
```
Copy the local API URL and `anon` key printed by `supabase status` into `.env` as `VITE_SUPABASE_URL` and
`VITE_SUPABASE_ANON_KEY`, then restart the Vite server. The local configuration disables email confirmation.

For a hosted project instead, set those same two `VITE_` values from the project's API settings. Never put a
service-role key in `.env` or any `VITE_` variable.
If hosted Auth requires email confirmation, users must confirm their address before signing in. Configure
SMTP in the Supabase dashboard so confirmation messages can be delivered to your users.

```bash
npm install
supabase start                      # prints API URL + anon key
supabase db reset                   # applies migrations + seed.sql (5 fictional demo users)
cp .env.example .env                # paste URL + anon key
cp supabase/functions/.env.example supabase/functions/.env
supabase functions serve --env-file supabase/functions/.env --no-verify-jwt   # terminal 2
eval "$(bash scripts/load-local-env.sh)" && npm run seed:demo                # demo documents
npm run dev                         # http://localhost:5173
```
Demo logins (local only): `owner.a@`, `owner.b@`, `viewer.c@`, `editor.d@`, `admin.e@trustvault.test` — password `TrustVault-Demo-1!`.

## Security model (summary)
* Browser untrusted. Identity = `auth.getUser(jwt)` in every function; role read from `profiles`, never from JWT/body.
* **Clients can only read**, through RLS. All writes go Edge Function → service-role RPC that checks permission,
  changes data and writes the audit row in **one transaction** (audit failure ⇒ request fails, no file served).
* One authorisation source of truth: `app.user_access()` + `app.access_allows()` in SQL.
* Storage bucket is private with **no client access** (restrictive policy); bytes only flow through functions. No signed URLs.
* Admin role grants audit/user administration only — zero document access (tested).
* Audit log: append-only triggers + SHA-256 hash chain. See `docs/audit-design.md` for what that does **not** prove.

Docs: `docs/` (architecture, threat model, authorization matrix, test matrix, audit design, schema, API, deployment, interview guide).

## Known limitations
No antivirus/PDF sanitising; metadata views (PostgREST reads) are not individually audited, content access is;
a download in progress or an already-downloaded copy cannot be recalled; the audit hash chain is not proof against a
DB superuser (export `head_hash` externally); uploads are buffered in function memory (default cap 5 MB, check current
Supabase Edge limits before raising); email confirmation is off locally—enable in production; no rate limiting on
auth-failure audit rows (possible log growth).
